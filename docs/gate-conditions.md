# ゲート条件の書き方

HARNESS.md のゲート条件は、審査役(`reviewer`)が「このフェーズを通してよいか」を決める唯一の物差しです。
審査役は書かれた条件しか確かめません。条件が甘ければ、何でも PASS になります。

## 良い条件の 3 つの性質

1. **誰が見ても同じ判定になる** — 「正しく」「問題なく」「適切に」「十分に速く」を使わない。
2. **審査役が自分で実行して確かめられる** — 実行するコマンド、開く画面、比べる相手が書いてある。
3. **証拠の形が決まっている** — 終了コード、件数、出力の一致、スクリーンショットなど、報告に貼れるものになっている。

## よくない書き方と、よい書き方

| よくない(人によって判定が変わる) | よい(誰が見ても同じ) |
| --- | --- |
| 正しく動く | `--help` を実行すると 4 つのコマンド名が表示され、終了コードが 0 |
| 前と同じ結果になる | 設定 12 項目の読み込み結果が、`docs/config-map.md` の期待値の表と一致する |
| クラッシュしない | 空のファイル・壊れたファイル・巨大なファイルの 3 つを読ませても、プロセスが終了せずにエラーを表示する |
| テストが通る | `npm test` の件数が前フェーズ以上で、失敗 0、skip が増えていない |
| 速くなった | 同じ入力で 5 回測った処理時間の中央値が 200 ms 以下(測り方は HARNESS.md の「環境」節) |
| 画面が崩れない | 幅 375 px と 1280 px で、見出し・本文・ボタンが重ならずに表示される(スクリーンショット 2 枚) |
| エラー処理が適切 | 保存先が書き込めないとき、入力内容を残したままエラーを表示し、ファイルを作らない |

## 条件の型

| 型 | 書き方の例 | 証拠 |
| --- | --- | --- |
| 終了コード | `{{コマンド}}` の終了コードが 0 | コマンドと末尾の出力 |
| 件数 | テストが N 件以上実行され、失敗 0 | テスト実行の生出力 |
| 出力の一致 | `{{コマンド}}` の出力が `{{期待値のファイル}}` と一致する | 差分(一致なら空) |
| 表との照合 | `docs/{{表}}.md` の全 N 項目が ✅ または理由付き ➖ | 表 |
| 画面 | `{{画面}}` で `{{要素}}` が表示される | スクリーンショット |
| 計測 | `{{測り方}}` で `{{値}}` が `{{閾値}}` 以下 | 測った値と回数 |
| 受け入れ項目 | `docs/acceptance-checklist.md` の全項目が ✅ または理由付き ➖ | 照合表 |
| 意地悪 | `{{おかしな入力}}` でも `{{守るべき動き}}` になる | 入力と結果 |

## 書いたら確かめること

- [ ] 条件を 1 つずつ読んで、「何を実行すれば判定できるか」を答えられる
- [ ] わざと壊したら落ちる条件が、少なくとも 1 つある(陽性コントロールに使う。HARNESS.md 付録 B)
- [ ] 正常系だけでなく、境界や失敗のときの動きを見る条件がある
- [ ] 実行環境が手元に無くて確かめられない条件は、その旨を書き、➖ で記録すると決めてある
- [ ] 1 フェーズの条件が、審査役が 1 回で確かめきれる量に収まっている(収まらなければフェーズを分ける)

## フェーズの分け方

- フェーズは「審査役が 1 回の審査で確かめきれる大きさ」に分ける。大きいフェーズほど、やるべき処理の書き漏らしが増える。
- 分け方は、チャットの plan モードで案を出させ、人が承認してから HARNESS.md に書いてよい。
  計画を見るときは、隣の機能とのつながり・状態への書き込み・画面や入力に埋まった決まり・書かれていない前提が
  計画に含まれているかを確かめる(`docs/acceptance-checklist.md` の観点と同じ)。
- 3 周で PASS しないフェーズは、モデルを変えるより、人がフェーズを分ける方が効くことが多い。
